# 2026-05-06 - Sesion 01

## Contexto de inicio

Se trabajo sobre el SaaS Laboratorio Academico PRO con foco en tres frentes: calidad visual del admin, estabilidad del flujo de creacion de proyectos y control operativo de IA por servicio. El objetivo fue dejar el entorno mas serio para administracion y mas robusto para pruebas reales entre Supabase y almacenamiento local.

## Que hicimos

- Se rediseno el sistema admin hacia una estetica oscura, sobria y mas ejecutiva.
- Se mejoro `Admin > Modelos & APIs` para mostrar estado operativo y alertas cuando un servicio queda sin tokens o con proveedor no disponible.
- Se corrigio la persistencia para que `ia por servicio` no se perdiera al guardar otras cosas en paralelo.
- Se redujo el problema de proyectos duplicados en `/projects/new` reutilizando el proyecto temporal en vez de crear otro en cada reintento.
- Se reparo el flujo de borrado del usuario para que desde dashboard solo oculte el proyecto.
- Se agrego respaldo admin de proyectos ocultados por usuario.
- Se agrego `Eliminar definitivo` solo en `Admin > Proyectos`.
- Se agrego `Restaurar` en `Admin > Proyectos` para reponer un proyecto ocultado por el usuario.
- Se reforzo el flujo `/projects/new`, `route-options` y `select-route` para que el proyecto exista tanto en Supabase como en snapshot local y no falle por buscarlo solo en memoria.

## Decisiones tomadas

- No cambiar automaticamente de proveedor de IA aunque un servicio se quede sin creditos, tokens o capacidad.
- El admin es quien decide manualmente cualquier cambio de proveedor.
- El borrado del usuario final no destruye informacion: solo la oculta.
- El borrado permanente queda reservado al admin como accion separada.
- Esta carpeta `docs/dev-sessions/` pasa a ser el mecanismo oficial de continuidad entre dispositivos.

## Bugs resueltos

- `ia por servicio` se reseteaba por una carrera de persistencia.
- El dashboard podia sembrar proyectos repetidos durante pruebas.
- La eliminacion desde dashboard mostraba errores confusos y no diferenciaba bien archivo vs borrado real.
- `Proyecto no encontrado o sin acceso` aparecia en `/projects/new` porque algunas rutas buscaban el proyecto solo en memoria local aunque hubiera nacido en Supabase.
- El admin no tenia forma de restaurar proyectos ocultados por el usuario.

- Seguir revisando la bibliografia y las fases finales con proveedor funcional para validar el flujo completo.
- Llevar el nuevo lenguaje visual del admin a otras secciones que todavia conservan estilo antiguo.
- Consolidar mejor el historial de sesiones si en el futuro se quieren multiples entradas por dia.

## Riesgos / no romper

- No revertir la regla de "sin auto-switch de proveedor".
- No mezclar `ocultar` del usuario con `eliminar definitivo` del admin.
- No volver a depender solo de memoria local en rutas que trabajan con proyectos creados en Supabase.
- Mantener `CURRENT.md` actualizado o el sistema de handoff pierde valor rapidamente.
